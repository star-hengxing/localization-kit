# ADR-0001: Go 纯文本核心与外部工具链边界

日期：2026-11-17 | 状态：accepted

## Context

本地化工作流涉及原文抓取、字幕/小说/游戏格式解析、术语匹配、大模型推理、人工审校、漫画视觉处理以及最终构建出书。若把所有抓取器、游戏引擎插件与模型进程管理耦合进单一核心，会导致构建臃肿、职责不清且难以跨场景复用。

## Decision

采用 **Go 核心文本引擎 + 明确外部边界** 架构：

1. **核心内置职责**：输入格式适配（`artc`、`vtt`、`jsonl`）、按组切分、术语与角色卡注入、OpenAI 兼容 API 请求、基础质量检查、追加式作业状态管理及导出。
2. **外部/独立模块边界**：
   - 模型部署、进程启停与 GPU 调度由外部服务或部署层负责，文本引擎通过 HTTP API 直连推理。
   - 游戏控制码保护与写回由游戏侧桥接脚本负责，双方通过稳定 ID 的 JSONL 交接。
   - 漫画视觉检测、OCR、擦除与嵌字由独立的 Python `src/image/` 模块负责，同样通过 `export-text` 导出 JSONL 接入核心文本工作流。
   - 小说抓取与最终 EPUB/PDF 构建由外部抓取器与 `artc` 工具链负责。

## Alternatives Considered

- **单一全包式单体**：在核心二进制内集成浏览器抓取、游戏引擎解包与本地推理调度。维护与跨平台构建成本过高，且难以独立演进各适配器。
- **纯脚本松散胶水**：无统一作业目录与状态机，中断恢复、术语签名和人工修订保护难以保持一致。

## Consequences

1. Go 核心保持轻量、无 GPU 运行时依赖，所有文本能力可单二进制测试与运行。
2. 漫画、游戏、小说等调用方通过标准 `jsonl` / `artc` / `vtt` 契约对接，复用同一套翻译、润色与质检引擎。
3. 命令行日志与错误输出到 `stderr`，机器可读摘要输出到 `stdout`；导出路径必须为新目录，避免覆盖中间状态。
